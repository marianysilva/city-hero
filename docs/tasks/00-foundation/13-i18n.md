## Context

Two-language support: pt-BR (default) and en-US (for tourist cities and international demos). All
user-facing strings are externalized in translation catalogs, plurals/dates/numbers are formatted by
ICU-style messages and `Intl`, and the language preference is persisted per user.

Even at MVP, hardcoded text is technical debt — once two cities run the app, adding more languages
must be a translation job, not a code refactor.

> **Architecture note (verified against current i18next/react-i18next/expo-localization docs,
> 2026-07):** i18next + react-i18next remains actively maintained and is the standard choice for
> ICU-style plurals in React/React Native — nothing here is deprecated. For only two locales at MVP
> scale, though, it is heavier than strictly necessary: a lighter `expo-localization` (for locale
> detection) plus a small typed key-value dictionary and `Intl.PluralRules` would satisfy every
> Acceptance Criteria scenario below with one fewer runtime dependency and no i18next
> backend/namespace machinery to configure. Flagging this trade-off for product/tech-lead awareness
> — not changing the architecture unilaterally, since i18next's namespace tooling and ICU
> `MessageFormat` support pay off once a third language or professional translators are added, and
> the effort delta at 2-locale scale is small.

## User Story

**As a** Citizen,\
**I want** the app in Portuguese (default) or English (toggleable),\
**In order to** use it in my native language without depending on system locale.

**As a** Frontend Developer,\
**I want** to externalize all strings,\
**In order to** support translations without touching component code.

## Acceptance Criteria

### Scenario · Default to system language

**Given** a fresh install on a device set to pt-BR\
**When** the app loads\
**Then** UI is in Portuguese\
**And** if the system is en-US, UI is in English\
**And** if the system is anything else, fallback to pt-BR

> **Reconciled during implementation** (product decision, 2026-07-22, see Status): the last line
> changed to **fallback to en-US**, not pt-BR — en-US is now the app-wide default for any
> non-pt/non-en device locale. pt-BR/en-US detection from a matching system locale is unchanged. A
> dev-only `EXPO_PUBLIC_DEFAULT_LOCALE` env var (see `apps/city-hero/.env.example`) can force either
> locale for local testing without changing the OS language.

### Scenario · Manual override

**Given** the user is on Settings\
**When** they pick "Idioma" / "Language"\
**Then** the app reloads strings without a full restart\
**And** the choice persists in local storage\
**And** subsequent app opens use the manual choice (not the system preference)

### Scenario · Plurals

**Given** the user has 0, 1, 5, or 27 supports on a report\
**When** the count badge renders\
**Then** it shows the correct plural form per locale\
**And** pt-BR uses "sem apoios" / "1 apoio" / "27 apoios"\
**And** en-US uses "0 supports" / "1 support" / "27 supports"

### Scenario · Dates and numbers

**Given** a report was created on 2026-04-21 14:30\
**When** the timestamp is rendered\
**Then** in pt-BR: "21/04/2026 às 14:30" or relative "há 2 horas"\
**And** in en-US: "Apr 21, 2026 at 2:30 PM" or "2 hours ago"\
**And** numbers follow locale separators (pt-BR uses `1.234,56`; en-US uses `1,234.56`)

### Scenario · Missing translation key

**Given** a developer renders a key that doesn't exist\
**When** the active locale doesn't have the key\
**Then** the fallback chain is checked: en-US, then the key itself as visible text\
**And** in dev mode, a console warning is logged\
**And** in prod, the missing key is logged to analytics for the translation team

### Scenario · RTL languages (future)

**Given** an RTL locale is added later\
**When** the user picks Arabic\
**Then** the layout flips automatically\
**And** existing layouts use `start`/`end` instead of `left`/`right`

### Behavior

- A translation hook is exposed and called in components to retrieve translated strings by key, with
  optional interpolation values (e.g., user name).
- Plurals use ICU `MessageFormat` (zero, one, other variants).
- Date formatting wraps a date-formatting library, selecting the locale based on the active
  language.
- Number formatting uses the platform's `Intl.NumberFormat`.
- Missing-key handling: dev warning, prod analytics log.

### Translation key naming

Keys are namespaced by feature (`home.welcome`, `report.supports_count`, `auth.login_failed`). Each
namespace maps to a JSON file in the locale folder.

### Editor support

A small VS Code snippet pack and an i18n-ally config make it easier for translators and developers
to find and add keys without searching files manually.

## Backend (FastAPI)

### Strategy

- Backend errors return a `code` and a `message_key` (not literal text).
- The frontend translates the key locally.
- Email templates have separate pt-BR and en-US versions, selected by the user's stored language
  preference.

### Email template location

```
apps/backend/src/templates/
├── verification_email/
│   ├── pt-BR.html
│   └── en-US.html
└── password_reset/
    ├── pt-BR.html
    └── en-US.html
```

## Database

The `users` table gains a `language` column (string, default `pt-BR`).

## Edge Cases

- **JSON file missing**: the i18n library falls back to default; a build-time check ensures all
  expected files exist.
- **Key with HTML in it**: use a translation component that supports interpolation of React nodes;
  never use raw HTML injection.
- **Language change during navigation**: causes re-render of the screen tree; ensure no broken
  state.
- **Mobile locale changes mid-session**: detected via app-state events; the app prompts the user to
  switch.
- **Long translation breaks layout**: design accommodates up to 1.6× length difference (German is
  the standard worst case to plan for, even if not in scope).

## Tests

- **Unit**: every component renders consistently with the translation hook mocked.
- **Integration**: switching language re-renders all visible text.
- **CI check**: a script verifies all keys in pt-BR exist in en-US (and vice versa).
- **CI check**: a regex-based scan catches hardcoded user-facing strings outside the locale folder.
